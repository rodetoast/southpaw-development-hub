# 공통 개발 지침

- 기존 기능과 개발 이력을 읽고 요청을 해결하는 범위만 수정합니다. 관련 없는 리팩터링, 관성적인 전체 시험과 중간 지시 교환을 피합니다. 승인 범위에서 기술 문제를 해결하고 관련 검증, 문서화, 안전한 Git 반영까지 진행합니다.
- 코드와 조건이 같은 시험 결과는 재사용합니다. 실제 실행, 기존 보고서에서 재사용한 결과, 미검증을 구분합니다.
- 프로젝트의 미커밋 내용을 보존하고 검토된 개발 브랜치에 관련 변경만 정상 커밋과 push로 남깁니다. 기존 프로젝트 상세 규칙을 함께 적용합니다. 지시가 충돌하면 우선순위와 작업 승인 범위를 확인합니다.
- 회사 공식 심볼과 앱 아이콘을 구분합니다. UI 변경은 실제 Windows에서 관련 DPI, 테마, 좁은 창과 주요 동작을 가능한 범위에서 확인합니다.
- 작업 파일, 설정, 설치 상태, 외부 호스트 계약과 기존 app_id를 보존합니다. 기존 직원에게는 현재 바로가기와 업데이트 버튼을 유지합니다.
- 서명, 해시, 신뢰 바인딩, 카탈로그 순번과 복구 보호를 유지합니다. 운영 게시, 저장소 소유권 변경, 실제 직원 환경 변경은 해당 범위의 승인을 확인합니다.
- 완료 기록에 소스 커밋, 구현, 검증·미검증, 버전, 배포 상태 및 후속 작업을 남깁니다. 의미 있는 변경만 중앙 요약에 반영합니다. 공개 범위에 맞춰 직원 자료, 경로, 개인키·토큰을 제외합니다.

## 개발 환경과 독립 검증

### 환경 선택과 역할

- ChatGPT는 기획·UX·시각 자료 제작뿐 아니라 기술 설계와 종합 관리감독을 주도합니다. 실제 접근 가능한 최신 소스·설계·검증 기록을 근거로 구조적 문제를 분석하고 해결 방향, 호환성, 검증 범위를 판단합니다. 개발 PC Codex는 로컬 환경 확인, 구현·수정·관련 검증과 개발 브랜치 관리를 담당합니다. 별도 Windows 테스트 PC Codex는 필요한 경우 독립적인 실행·실사용 검증과 원인 조사, 재현·증거 수집을 담당합니다.
- 복잡한 구조 변경, 데이터 계약, 외부 호스트 연동, 자동 업데이트·서명·복구 등 영향이 큰 과제에서는 ChatGPT가 가능한 범위에서 실제 소스를 먼저 분석하고 대안과 위험을 비교하여 권장 설계, 변경 범위, 보존할 계약, 예외 처리와 완료·검증 기준을 구체화합니다. 필요하면 승인된 설계 명세를 프로젝트의 적절한 문서 경로에 등록하고 기준 커밋과 함께 전달합니다. 직접 확인하지 못한 로컬 코드·바이너리·실행 환경은 Codex의 확인을 활용하며 추측을 검증 사실로 취급하지 않습니다.
- 설계는 구체적으로, 구현은 자율적으로 진행합니다. Codex는 실제 코드와 로컬 환경에 맞는 구현 방법을 선택하고 설계의 결함이나 더 나은 대안을 발견하면 근거와 함께 제시합니다. 단순하거나 명확한 작업은 별도 설계 단계·장문 명세·중간 보고 없이 Codex가 직접 진행할 수 있습니다. GPT와 Codex가 동일한 분석을 관성적으로 반복하지 않으며 중요한 제품·보안·호환성 결정과 승인 경계는 유지합니다.
- 추론 수준은 작업의 복잡도와 위험에 맞춰 선택합니다. 일반 구현·검증은 중간 수준을 기본적으로 고려하고 복잡한 기술 설계, 원인 불명의 장애, 보안·자동 갱신·복구는 높은 수준을 활용할 수 있습니다. 설정 수준만으로 어느 환경의 판단이 항상 우월하다고 가정하지 않으며 실제 코드 접근, 실행 증거와 검증 가능성을 함께 고려합니다. 모델·추론 설정 변경을 일률적으로 요구하지 않습니다.
- 이 검증 분담은 런처를 포함한 모든 Southpaw Games 프로그램에 적용합니다. 변경 위험과 목적, 기존 결과의 유효성, 각 PC의 설치 프로그램·버전·라이선스·권한·데이터 격리 가능성을 먼저 확인합니다. 실제 GUI 검증이 필요하지 않으면 테스트 PC 사용은 필수가 아닙니다. 코드와 시험 조건이 달라지지 않았다면 기존 결과를 재사용합니다. 예를 들어 PS2ASE `f8fb6d4`의 실제 Photoshop 일반 전송은 동일 조건에서 다시 시험하지 않습니다.
- 별도 테스트 PC에는 Aseprite가 설치되었다는 2026-11-27 사용자 보고가 있습니다. 설치 버전·실행 경로·라이선스·프로필과 실제 동작 가능 여부는 필요한 시험에서 확인합니다. Aseprite 실제 호스트 연동·Trust·스크립트·물리 단축키 검증은 해당 환경에서 안전하게 수행 가능한 범위에 한해 활용합니다. Photoshop은 2026-11-27 사용자 재확인 기준으로 별도 테스트 PC에서 여전히 사용할 수 없습니다. Photoshop 또는 실제 양방향 호스트 연동 검증은 가능하다고 가정하지 않으며, 대체 편집기나 합성 데이터의 결과를 실제 Photoshop 호스트 검증과 구분합니다. 호스트 미설치 안내와 독립 기능 검증도 필요에 따라 수행할 수 있습니다. 실제 호스트가 필요한 검증은 이미 적합한 호스트가 설치된 환경을 우선하고, 없으면 미검증으로 기록합니다. 추가 설치·라이선스 사용·보안 설정 변경은 필요성과 가능성을 먼저 검토하고 사용자 승인 없이는 실행하지 않습니다. Aseprite 설치 자체가 Windows 사용자·설치 데이터·Shell 격리 환경의 확보를 뜻하지 않으며, 환경이 바뀌면 실제 상태를 확인합니다.
- 로컬 전용 프로젝트는 원격 소스 확보가 가능한지부터 판단합니다. 검증만을 위해 저장소 공개·이전이나 시험 Release 생성을 강제하지 않습니다.

### 소스 실행과 Windows Use

- 패키징 자체가 검증 대상이 아니라면 지정된 소스 커밋에서 직접 실행하는 방식을 우선 검토합니다. 프로젝트별 실제 기술과 실행 절차를 따르며 Python 전용 가상환경, Node/Electron 의존성, Godot 등 필요한 환경을 분리합니다. 동일한 실행 방법을 모든 프로그램에 강제하지 않습니다.
- 기능·UI·UX·파일 처리·설정 저장·성능·DPI·호스트 연동은 소스 실행으로 유효하게 검증할 수 있는 범위에서 확인합니다. EXE·ZIP·시험 Release는 별도 PC라는 이유만으로 만들지 않습니다. 패키징과 설치·배포 경계 검증은 [배포 절차](RELEASE_GUIDE.md)를 따릅니다.
- 개발 PC Codex는 토큰 사용량을 줄이기 위해 Windows Use를 최소화합니다. 소스 분석·구현·자동 테스트·CLI/PowerShell·로그 분석을 우선하고, 파일·해시·Git·프로세스·설정·레지스트리·의존성 확인에 GUI를 사용하지 않습니다.
- 실제 화면 조작, 물리 입력, 외부 프로그램 GUI 및 사용성 검증이 필요하면 별도 테스트 PC에 우선 인계합니다. 테스트 PC에서 수행할 수 없는 실제 호스트 검증(예: Photoshop 연동)만 개발 PC에서 필요한 범위로 수행하고, Windows Use는 그중 코드·CLI·로그·자동화로 대체할 수 없는 조작에만 사용합니다. 어느 PC에서도 안전하게 수행할 수 없으면 미검증으로 기록합니다.

### 테스트 PC 인계와 기록

- 인계는 프로그램 번호와 명칭(런처는 번호 없음), 저장소·실제 개발 브랜치·기준 커밋, 검증 목적, 관련 상태/검증 문서, 필요한 환경과 데이터 보호 조건 중심으로 간결하게 합니다. 테스트 PC는 중앙 지침과 프로젝트 지침을 읽고 실제 HEAD 및 시험 가능 조건을 확인합니다. 브랜치의 이후 변경과 검증한 커밋을 구분합니다.
- 테스트 PC는 기본적으로 제품 소스 읽기·검증·원인 조사에 집중합니다. 개발 PC와 같은 개발 브랜치에 제품 변경을 동시에 반영하지 않습니다. 제품 수정이 필요하면 사용자 승인 후 별도 브랜치에서 작업하고 개발 담당자가 검토·통합합니다. 기존 미커밋 작업을 보존하며 강제 reset/clean/checkout을 하지 않습니다.
- 별도 작업 폴더만으로 설정·설치 상태가 격리됐다고 가정하지 않습니다. 필요하면 테스트용 데이터 프로필·가상환경·Windows 시험 계정·합성 파일을 사용합니다. 기존 사용자 문서·설정·설치 프로그램·런처 상태를 보호하며 승인 없이 기존 호스트 종료, 데이터 초기화, 보안 설정 변경을 하지 않습니다.
- 결과에는 기준 소스 커밋, 실제 시험 환경(필요한 호스트/버전과 소스 또는 빌드 실행 여부), 재현 절차, 기대/실제 결과, 통과·실패·미검증 범위, 필요한 로그·시각 자료와 개선 의견을 기록합니다. 합성/Mock 검증과 실제 호스트 검증을 구분합니다.
- 공개 가능한 의미 있는 결과는 기존 [협업 게시판](COLLABORATION.md)과 시각 자료 공유 규칙을 활용합니다. 공유 중인 개발 브랜치에 증거를 동시에 push하지 말고, 기존 관련 이슈의 댓글이나 필요한 경우 프로젝트 라벨이 붙은 이슈로 인계합니다. 대표 파일을 Git에 남길 필요가 있으면 별도 검증자료 브랜치에 증거만 커밋하고 기준 소스 커밋과 고정 링크를 기록하거나 개발 담당자가 기존 자료 경로에 선별 통합합니다. 민감 자료는 공개하지 않고 기존 승인된 비공개 증거 경로 또는 로컬에 보존합니다. 모든 로그·화면의 업로드나 모든 시험의 신규 이슈 생성을 요구하지 않습니다.
- 작업 목적에 따라 구현 → 관련 검증 → 개발 브랜치 반영 → 필요한 독립 검증 → 결과 검토 및 보완 → 사용자 결정에 따른 배포 후보 제작 순서를 활용합니다. 작은 변경마다 전 단계를 강제하지 않으며, 소스 검증을 패키징/운영 배포 검증으로 간주하지 않습니다. 별도 Codex 세션은 자동 호출하거나 백그라운드 동기화되지 않습니다.

## 디자인 시안과 구현 검토 자료

- 각 프로그램의 소스 저장소에서 기존 자료 구조를 우선 사용합니다. 정해진 위치가 없으면 사용자가 제공한 자료나 GPT 시안은 `docs/design-references/`에, 실제 구현 화면·변경 전후 비교·동작 검증은 `docs/ui-reviews/`에 둡니다. 시안과 실행 결과의 종류를 명시합니다.
- 의미 있는 UI 또는 시각 기능 변경마다 결과를 설명할 최소한의 자료를 남깁니다. 화면 캡처 외에도 픽셀 이펙트, 애니메이션, 이미지 처리 결과, 타임라인 동작 등 기능에 맞는 형식을 씁니다. 움직임이 핵심이면 짧은 GIF나 영상을 사용합니다.
- 자동 촬영이 가능하면 Codex가 실제 구현을 직접 촬영합니다. 이미 같은 화면 상태를 입증하는 자료를 재사용하고, 비교가 필요할 때만 변경 전후의 대표 자료를 보존합니다.
- 갤러리 설명에 자료의 종류, 촬영하거나 검토한 버전, 구현 소스 커밋과 화면 상태를 기록합니다. 시안은 제공 출처를 기록하고 빌드 검증 근거로 사용하지 않습니다. 공개 가능한 자료만 커밋하며, 직원 정보·인증 정보·비공개 게임 자료와 사용자 경로가 화면이나 영상에 노출되지 않는지 확인합니다.
- 완료 보고에는 GitHub 갤러리 URL과 대표 이미지 또는 동작 자료의 **커밋 고정 직접 URL**을 함께 제공합니다. 의미 있는 변경은 프로젝트 상태 문서에도 갤러리를 연결합니다.
- 다른 프로그램에 참고가 되는 갤러리와 대표 자료는 중앙 허브의 기존 `projects/<project>.md` 요약에서 링크합니다. 중요한 시각 디자인 결정은 [결정 기록](DECISIONS.md)에 남깁니다. 중앙에는 링크를 관리하고 파일은 프로젝트 저장소에 둡니다. 통합 참조 파일을 재생성하면 결정 기록과 프로젝트 요약에 있는 대표 링크가 포함됩니다.

### GPT 디자인 시안 직접 공유

- 모든 프로그램에 공통 적용합니다. 사용자가 구현에 참고하도록 선정하거나 등록을 승인한 GPT 디자인 시안은 GitHub 쓰기 접근이 실제로 가능한 경우 GPT가 해당 프로그램의 기존 디자인 자료 경로 또는 `docs/design-references/`에 직접 등록하는 방식을 우선합니다. 모든 임시 시안을 보관하지 않습니다.
- 대상 저장소, 활성 개발 브랜치, 기존 파일 및 쓰기 권한을 확인하고 관련 참고 자료만 커밋합니다. 기존 자료를 무단 덮어쓰지 않으며 제품 코드, 배포 카탈로그 및 운영 아티팩트는 이 절차로 변경하지 않습니다. 공개 범위와 기존 자료 보호 규칙을 적용합니다.
- 기능에 맞춰 PNG, SVG, HTML/CSS, Markdown 등으로 전달합니다. 필요한 경우 디자인 의도, 동작, 상태, 색상·여백·타이포그래피 등의 구현 참고 정보를 함께 기록합니다. HTML/CSS 시안은 실제 제품의 구현 기술 변경을 요구하는 것이 아닙니다.
- 직접 등록한 시안은 커밋과 파일 경로 또는 커밋 고정 URL을 Codex 지시와 함께 전달합니다. Codex는 원문을 읽고 기존 기능과 프로젝트 기술에 맞춰 구현하며 실제 결과는 `docs/ui-reviews/`에 구분해 기록합니다. GPT는 실제 접근 가능한 결과를 검토합니다.
- GitHub 연결만으로 모든 파일 형식의 쓰기·읽기나 자동 작업 전달이 보장되지 않습니다. 등록 결과를 확인하고, PNG 등 바이너리 업로드가 지원되지 않거나 저장소가 로컬 전용이거나 쓰기 접근이 불가능하면 전달 가능한 파일을 제공하여 기존 Codex 등록 절차를 사용합니다. 승인된 자료의 실제 등록 전까지 등록 완료로 보고하지 않습니다.

### GitHub 접근 환경별 검토

- GitHub 연결 및 실제 접근이 가능한 환경에서는 최신 원문과 커밋 고정 갤러리·이미지·동작 자료를 우선 참조합니다. 연결하지 않은 환경에서도 공개 URL을 실제로 열 수 있으면 직접 참조합니다.
- 접근 권한과 이미지 자체의 열람 가능 여부는 계정·도구·저장소별로 확인합니다. 링크나 설명만 읽은 경우 실제 시각 검토로 기록하지 않습니다. 한 환경의 성공을 다른 환경에 일반화하지 않으며 계정 연결을 일률적으로 요구하지 않습니다.
- 직접 접근이 불가능하면 개발 보고서로 확인 가능한 내용을 먼저 검토하고 실제 화면이 필요한 경우에만 아래 합본 PNG를 사용합니다. 기존 GitHub 원본과 커밋 고정 링크는 유지하며 동일 조건에서 반복 접근 시험이나 별도 호스팅 구축을 하지 않습니다.

### GPT 검토용 PNG 만들기

- 의미 있는 UI 또는 시각 기능 변경을 마칠 때, 직접 열람이 불가능한 환경을 위한 대체 수단으로 이미 보관한 대표 화면에서 GPT 첨부용 합본 PNG를 Codex가 생성합니다. 직접 열람이 가능한 환경에서는 사용자에게 합본 첨부를 요구하지 않습니다. 화면마다 제목과 상태(예: 변경 전후, 테마, DPI, 실행 조건)를 적고 합본 제목에는 프로젝트와 버전 또는 커밋을 넣습니다.
- 원본 화면을 축소하거나 잘라 맞추지 않습니다. 한 장이 너무 커지면 번호가 붙은 PNG 여러 장으로 나누고, 원본 화면 하나가 기준보다 크면 원본 해상도로 별도 페이지에 둡니다. 영상이 필요한 경우에는 갤러리의 원본 링크도 함께 제공합니다.
- 완료 보고에 GitHub 갤러리와 커밋 고정 대표 자료 링크, 생성된 합본의 로컬 경로를 함께 남깁니다. 합본은 첨부용으로 두고 기존 GitHub 원본과 갤러리를 유지합니다. 웹 ChatGPT가 링크를 열지 못하면 [AI 시작 안내](AI_START_HERE.md)의 검토 순서에 따라 실제 화면 확인이 필요한 경우에만 합본을 첨부합니다.

허브 루트에서 Python과 Pillow 10.1 이상으로 [합본 스크립트](../tools/make_review_sheet.py)를 실행합니다. 화면마다 `--view`에 기존 이미지 경로, 화면 제목, 상태를 순서대로 지정합니다. 아래 예시의 경로는 실제 검토 파일과 출력 위치로 바꿉니다.

```powershell
python tools/make_review_sheet.py --title "프로젝트 / v1.2.3" --output "C:/Dev/reviews/project-v1.2.3.png" --view "C:/Dev/reviews/before.png" "작업 화면" "변경 전 · 다크 · 100%" --view "C:/Dev/reviews/after.png" "작업 화면" "변경 후 · 다크 · 100%"
```

Windows에서는 기본 한글 폰트를 사용합니다. 다른 환경에서 한글 제목이 필요하면 `--font`에 사용할 한글 폰트 파일을 지정합니다.

## GitHub 개발 인증 및 중앙 허브 갱신

- 개발 작업에는 기존 `rodetoast` 인증을 우선 사용합니다. `gh auth status`와 `gh api user --jq .login`으로 CLI 계정을 확인합니다. Git의 커밋 작성자 이름·이메일과 CLI의 로그인 계정만으로 실제 Git push 계정을 판단하지 않습니다.
- PS2ASE 0.3.7 인계에서는 기본 Git HTTPS helper가 `toast-source`를 선택했습니다. 이 계정은 PS2ASE에 쓸 수 있었지만 중앙 허브에는 읽기만 가능해 HTTP 403이 발생했습니다. 다른 개발 저장소에서도 같은 helper 경로를 확인했습니다.
- 여러 계정이 있는 환경에서는 기존 인증을 유지하고, 아래처럼 **현재 대상 저장소의 정확한 HTTPS push URL에 한해서** GitHub CLI helper를 사용합니다. 운영 배포 도구에는 이 개발 명령을 적용하지 않습니다.

### Windows PowerShell 예시

허브 작업 사본에서 GitHub CLI가 PATH에 있는 상태로 실행합니다. 이미 설치된 실행 파일이 PATH에 없다면 해당 세션에서만 찾을 수 있게 설정합니다. 먼저 실제 GitHub push URL과 `gh api user --jq .login`의 결과가 각각 의도한 저장소와 `rodetoast`인지 확인합니다.

```powershell
$target = git remote get-url --push origin
$key = "credential.$target"
git -c "$key.helper=" -c "$key.helper=!gh auth git-credential" -c "$key.username=rodetoast" push --dry-run origin HEAD:refs/heads/main
```

허브에서 최신 `origin/main`과 정상 fast-forward 관계이고 dry-run이 통과하면 같은 명령에서 `--dry-run`을 빼고 문서 변경을 반영합니다. 제품 소스 작업에서는 그 저장소의 검토된 개발 브랜치로 대상을 바꿉니다. 보호 정책이 PR을 요구하면 해당 절차를 따릅니다. Dry-run은 원격 브랜치를 바꾸지 않으며 모든 서버 측 보호 규칙 통과를 보장하지 않습니다.

### HTTP 403이 발생하면

1. CLI를 덮어쓸 수 있는 `GH_TOKEN`·`GITHUB_TOKEN`의 **존재만** 확인합니다. 실제 push URL과 fetch URL, URL 치환, HTTPS helper의 적용 범위 및 `credential.useHttpPath`를 확인합니다.
2. 선택된 인증의 저장소 쓰기 권한, 토큰 권한 범위, 브랜치 보호 및 Ruleset을 확인합니다. 자격 증명과 토큰을 화면이나 로그에 출력하지 않습니다. 확인할 수 없는 권한은 미확인으로 남깁니다.
3. 쓰기가 막히면 검토한 문서 커밋과 패치를 안전한 로컬 위치에 보존합니다. 최신 원격 기준, 로컬 커밋, 충돌과 미반영 범위를 인계합니다. 원격에서 문서를 확인한 뒤에만 동기화 완료로 기록합니다.
