# 배포 후보와 운영 Release

## 개별 프로그램 담당

1. 각 프로젝트의 빌드 절차를 따릅니다. 소스 커밋, 표시 버전, app_id, 변경 내용과 검증·미검증 상태를 기록합니다.
2. 운영 ZIP 이름은 `app_id--release_id.zip`입니다. 승인된 onefile 또는 onedir 구조에서 내부 EXE, 작업 디렉터리 상대 경로, 필수·보존 경로를 확인합니다. 후보 ZIP, ZIP 크기, ZIP 및 EXE SHA-256과 릴리스 노트를 함께 전달합니다.
3. 프로젝트 상태를 갱신해 런처 담당자에게 인계합니다. 프로젝트 소스 push와 직원용 운영 게시는 별도 절차입니다.

## 런처 담당

1. 기존 런처의 승인 ZIP 가져오기와 카탈로그·설치 엔진으로 경로, 크기, SHA-256 및 보존 계약을 확인합니다. 런처 관리형 GUI는 `launcher-package.json`과 Bootstrap ready/confirmed 및 실패 복구 계약을 확인합니다.
2. 실제 원격 Latest와 서명 카탈로그를 시작점으로 확인합니다. 올바른 저장소 ID, catalog ID, 채널별 증가 sequence를 확인하고 운영 Ed25519 서명 `catalog.sig.json`을 검증합니다. 기존 호환 채널과 롤백 보호를 유지합니다.
3. 정확한 채널·태그·자산의 사용자 승인 후 Draft 자산을 재다운로드해 크기·SHA-256·서명을 확인합니다. 승인 범위에서 정식 게시하고 공개 HTTPS 및 Latest와 필요한 업데이트 호환성을 검증합니다. 동일 순번의 자산을 다른 바이트로 덮어쓰지 않습니다.
4. 로컬 후보, 서명 후보, 실제 공개, Latest 확인 결과를 구분해 프로젝트와 허브에 기록합니다.

신규 직원 Setup은 별도 산출물입니다. 기존 직원은 현재 바로가기와 업데이트 버튼을 계속 사용합니다. [현재 배포 채널](PROJECTS.md)
